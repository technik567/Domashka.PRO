## 1. Опубликовать фронтенд в Cloudflare Pages

### Проще всего: прямая загрузка готового ZIP

1. Скачайте **`Domashka_PRO_Cloudflare.zip`**, а не `Domashka_PRO_Portable.zip`.
2. В Cloudflare откройте **Workers & Pages → Create application → Pages → Upload assets / Direct Upload**. Названия пунктов могут меняться; нужен статический Pages-проект, не Worker.
3. Выберите имя проекта, загрузите ZIP (или его распакованное содержимое) и нажмите **Deploy**. В корне загрузки должны быть `index.html` и `_headers`, без внешней папки-обёртки. Никакие пароли/токены/Node.js для этого не нужны.
4. Откройте **фактический HTTPS-адрес, выданный Cloudflare**, и пришлите этот адрес в Arena. Не угадывайте домен по выбранному имени.

В ZIP уже есть публичные URL/key существующего Supabase-проекта. `siteUrl=auto` берёт origin реального HTTPS-сайта; **это не автоматическая настройка Auth allowlist или Edge Origins**. `file://`, HTTP и GitHub Pages для этой сборки отклоняются. Регистрация остаётся закрытой до SMTP/CAPTCHA. После добавления публичного Turnstile site key пакет нужно пересобрать/загрузить снова.

Direct Upload и Git-интеграция — разные способы проекта Pages. Если нужен автоматический build из Git, выбирайте следующий вариант при создании, а не ждите, что загруженный вручную проект сам свяжется с репозиторием.

### Альтернатива: автоматическая сборка из Git


Прямой интеграции Cloudflare с Arena в этом сеансе нет. Выполните этот шаг в **своей панели Cloudflare**, не передавайте пароли/токены в чат.

1. Откройте Workers & Pages → создание **Pages**-проекта → подключение Git-репозитория `technik567/Domashka.PRO`.
2. **Пока PR не объединён**, выберите production branch **`arena/62f26394-domashka-pro`**. В `main` пока 4.2; создавать другую ветку для этого не нужно. После отдельного решения о слиянии можно переключить источник Pages на `main`.
3. Framework preset: **None**. Build command: **`npm run build:cloud`**. Output directory: **`.cache/cloud-site`**. Корень сборки — корень репозитория. Нужны Node.js **22+** и Python **3.11+**; для образа сборки можно задать `NODE_VERSION=22` и `PYTHON_VERSION=3.11`.
4. Выберите имя проекта и используйте **реальный HTTPS-адрес, показанный Cloudflare**, а не вымышленный пример. Если Cloudflare изменил предложенное имя, поправьте Site URL и повторите сборку.
5. Добавьте нижеуказанные **публичные** переменные сборки. `DOMASHKA_SITE_URL` — `auto` до получения домена или реальный адрес из предыдущего пункта с `/` в конце. Сохраните и дождитесь успешного deployment.

```text
DOMASHKA_SUPABASE_URL=https://zgfjfngcwtupqyirwfha.supabase.co
DOMASHKA_SUPABASE_PUBLISHABLE_KEY=sb_publishable_LNQuFvv9MW97eqMjPIdp1g_p0qnlL9M
DOMASHKA_SITE_URL=auto
```

**Publishable key намеренно публичен**: это не AI-ключ, не пароль и не service-role secret. Доступ к данным всё равно требует пользовательского входа и серверных прав. Если ключ будет отозван/заменён, обновите переменную сборки. Не используйте `service_role`/`sb_secret_…` вместо него.

Ключ Turnstile (`DOMASHKA_TURNSTILE_SITE_KEY`) добавьте после создания CAPTCHA для реального домена, затем повторите сборку. До готовности всей настройки регистрация должна оставаться закрытой. Без CAPTCHA у включённой на сервере защиты вход работать не будет.

**Пришлите в Arena только получившийся HTTPS-адрес сайта** — это не секрет. По нему можно завершить разрешённые редиректы и Origin обеих функций. Без настоящего адреса они намеренно не угадываются и не разрешаются маской `*`.

Если выбранный хостинг недоступен в вашей сети, сначала проверьте другой HTTPS-хостинг и обновите адреса в конфигурации. Проверка в среде разработки не подтверждает доступность на вашем ПК/телефоне.

## 2. Закончить Auth, Origin и почту

В панели Supabase / средствами владельца:

- Auth → URL Configuration: заменить стартовый `http://localhost:3000` на настоящий HTTPS Site URL, разрешить **только точные** redirect URLs. Приложение ещё не собрано с этим стартовым localhost-адресом; браузер не должен использовать его для облака.
- Edge Functions → Secrets (для `family-admin` и `web-search`): задать `DOMASHKA_ALLOWED_ORIGINS` равным **origin сайта без завершающего `/`**. Не `*`. Можно задать точный список через запятую, если действительно используются несколько доменов.
- Auth: оставить email confirmation; задать минимум **8 символов** и включить безопасную смену пароля. В новом проекте минимальная длина пока была стандартной **6** — клиент требует 8, но серверную настройку необходимо довести до 8 отдельно.
- Подключить **custom SMTP**, подтвердить отправителя по требованиям провайдера, проверить лимиты Supabase и SMTP. Стандартная почта Supabase не годится для публичной регистрации/восстановления; добавление всех родителей в команду проекта не заменяет SMTP.
- Установить шаблоны **Confirm signup** и **Reset password** с `#token_hash=…` из [CLOUD_SETUP.md](CLOUD_SETUP.md#3-настроить-auth-письма-и-captcha), чтобы письмо можно было открыть на другом устройстве.
- Настроить Turnstile в Cloudflare и Supabase Auth: **site key** — во фронтенд-сборку, **secret** — только в Auth CAPTCHA settings. Пересобрать сайт.
- Только после этого разрешить signup и выполнить контролируемую регистрацию/восстановление на тестовом адресе вне команды Supabase. Если что-то не готово, оставьте signup выключенным.

SMTP-пароль, admin/service-role keys, пароль базы и секрет Turnstile не присылайте в чат и не добавляйте в Git. Пароль базы использовался только при создании; для прямого SQL-подключения при необходимости задайте новый в панели базы. Обычному пользователю приложения он не нужен.

Для полного поиска также выполните [настройку Tavily Free](AI_FEATURES.md#поиск-tavily). Не включайте PAYG, автопополнение и платную подписку.

## 3. Проверить ПК и телефон

Сделайте [живой приёмочный прогон](CLOUD_SETUP.md#6-обязательный-приёмочный-прогон-на-настоящем-проекте): письмо и восстановление, родитель, ребёнок без почты, один аккаунт на двух устройствах, дневник/фото, конфликт, потеря сети, проверка карточек, домашка и права другой семьи. На iPhone проверяйте Safari и реальные разрешения голоса/камеры отдельно; viewport Chromium — не физический iPhone.

Уже сделанные локальные проверки и их ограничения перечислены в [QA_4.3.md](QA_4.3.md) (и историческом QA 4.2). Техническая установка схемы и статус `ACTIVE` функции не заменяют этот сценарий.

## Что остаётся автономным

`Domashka_PRO.html` в Git и переносимом ZIP **не содержит облачной конфигурации**: он сохраняет данные локально, как прежде. Не считайте отправку этого файла переносом аккаунтов или истории. Онлайн-вход появится на отдельно настроенном сайте. Старые данные переносятся явно из раздела «Семья → Перенос и резервная копия учебных данных», без паролей, сеансов и API-ключей.
