# Облачная Домашка.ПРО 4.3: настройка владельцем

**Состояние исходников не равно работающему сервису.** В этой поставке есть миграции, браузерный клиент, серверная функция и проверки. Проект Supabase, Turnstile и публикация Cloudflare должны быть настроены владельцем. Успех локальных тестов не подтверждает работу GoTrue/Storage или синхронизацию реальных устройств.

## Почему сайт, а не `.exe`

Один HTTPS-сайт работает на ПК, Android и iPhone без установки отдельного приложения. `.exe` сам по себе не объединяет аккаунты: ему всё равно нужны серверная авторизация и база. Выбран стартовый вариант **Cloudflare Pages или Workers static assets (интерфейс) + Supabase Auth/Postgres/private Storage (аккаунты и данные)**. GitHub остаётся источником кода и автономного HTML.

GitHub Pages не используется для облачного входа: официальная документация предупреждает о чувствительных операциях, включая отправку паролей. Существующий Pages workflow оставлен только для прежнего **локального** клиента, без облачной конфигурации. `prepare_cloud.py` и браузерный валидатор не разрешают `*.github.io` как Site URL.

### Бесплатно — в пределах лимитов, не навсегда без ограничений

По проверенным 06.11.2026 страницам Supabase Free: 50 тыс. MAU, 500 МБ БД, 1 ГБ Storage, 5 ГБ egress и отдельно 5 ГБ cached egress, два активных проекта; проект может приостанавливаться после недели неактивности. Это не гарантия доступности и не обещание бесплатной работы при любом числе пользователей.

Cloudflare Pages Free: 500 сборок/месяц, 20 тыс. файлов, 25 MiB на файл. Для этого статического приложения Pages Functions не требуются: защищённая функция размещается в Supabase. Проверяйте актуальные условия обоих сервисов перед запуском. Код не включает платный тариф автоматически.

**Почта больше не является условием.** Родитель регистрируется по логину/паролю и получает 10 одноразовых резервных кодов. SMTP и покупка почтового домена не нужны. Сервер использует технические идентификаторы Supabase Auth, не реальную почту человека. [Контракт и восстановление](AUTH_USERNAME.md).

## 1. Подготовить проект и адрес

1. Создайте отдельный проект Supabase в своём аккаунте/организации, при необходимости выберите подходящий регион ЕС. Не применяйте эти миграции к базе другого приложения.
2. Создайте статический проект Cloudflare Pages и определите окончательный адрес `https://ИМЯ.pages.dev/` либо свой HTTPS-домен. Публичную регистрацию открывайте только после завершения следующих шагов.
3. Проекту нужны URL `https://REF.supabase.co` и **publishable key** (либо прежний **anon** JWT). Это публичная конфигурация браузера, не полномочия администратора.
4. `service_role`, `sb_secret_…`, пароль базы, резервные коды и секрет CAPTCHA **никогда не копируются в HTML, репозиторий или чат**. Административные значения допустимы только в защищённой среде серверной функции/панели сервиса.

Если работа выполняется через Arena, подключите Supabase и нужный хостинг в интерфейсе подключённых приложений. Не присылайте пароли, токены или коды подтверждения сообщением.

## 2. Применить базу — один раз, по порядку

Нужен Supabase CLI, авторизованный владельцем проекта. Не запускайте эти команды против случайного или чужого проекта:

```sh
supabase login
supabase link --project-ref ВАШ_REF
supabase db push
```

CLI применит все SQL-файлы `supabase/migrations/` по порядку (исходные шесть, серверный поиск и новая миграция `username_recovery`):

- профили, семейные связи, CAS-документы, статистика, задания и права;
- попытки проверки карточек и одноразовые награды;
- воспроизводимый банк: 1700 карточек / 4881 короткая проверка;
- закрытый bucket `domashka-photos`, правила фотографий и явный импорт;
- одноразовые разрешения для Auth-admin и отзыв старых сеансов при смене пароля;
- небольшие метаданные для опроса и отдельная ограниченная сводка ученика;
- атомарные квоты серверного поиска;
- логин без почты, 10 хешей одноразовых кодов, квоты/разрешения и атомарное восстановление.

Альтернатива — SQL Editor проекта, те же файлы строго последовательно. Первые миграции рассчитаны на новую базу приложения и должны быть установлены **до регистрации пользователей**. Ручной повтор уже применённой миграции не является обновлением. Не отключайте RLS и не выдавайте `anon`/`authenticated` права записи в профили/статистику/семейные связи.

Схема `domashka_private` не должна быть в списке exposed API schemas. Не публикуйте Auth-таблицы, приватный банк ответов, попытки, квитанции и admin tickets. Не добавляйте широкие публичные политики к bucket. Установка в проект с посторонними permissive-политиками требует отдельного аудита.

## 3. Настроить Auth без почты и Turnstile

- Включить email/password-провайдер для технических идентификаторов, **оставить нативную регистрацию выключенной** (`disable_signup=true`). Публичный пользователь регистрируется через защищённую `account-access`, а не напрямую `auth.signUp`. `mailer_autoconfirm=false` можно оставить: сервер подтверждает только собственные технические идентичности через admin API. Anonymous/phone sign-ins не нужны.
- Minimum password length — **8**. Включить **требование текущего пароля** при самостоятельной смене. Клиент передаёт `current_password` и использует отдельную временную проверочную сессию. Не включать почтовые уведомления о смене пароля/адреса для недоставляемых технических адресов.
- Site URL/redirect allowlist — точный HTTPS-адрес, без wildcard. Workers-адрес совместим: переносить работающий сайт в Pages не нужно.
- Создать настоящий виджет Cloudflare **Turnstile** с точным hostname сайта, без схемы/пути.
- **Публичный site key** → переменная сборки `DOMASHKA_TURNSTILE_SITE_KEY`, затем пересобрать и загрузить клиент.
- **Secret key** → Supabase Auth CAPTCHA settings, provider **Turnstile**: защита обычного входа/повторной проверки пароля.
- **Тот же secret key** → Supabase Edge Secrets **`DOMASHKA_TURNSTILE_SECRET_KEY`**: отдельная серверная проверка публичной регистрации/восстановления в `account-access`. Admin API не проверяет CAPTCHA вместо этой функции. Нельзя ограничиться настройкой только Auth.
- В виджете клиент задаёт action `domashka-auth`; Edge проверяет action и точный hostname. Стандартные тестовые секреты отклоняются. Без настоящего секрета сервер возвращает 503, а без public site key новый клиент не разрешает отправку формы регистрации/восстановления.

SMTP и шаблоны писем для этой регистрации **не настраивают**. Восстановление — по одному из десяти кодов; при утере всех кодов и пароля самостоятельного восстановления нет. Совместимость входа прежних email-аккаунтов сохранена; после входа они могут получить коды. Математический вопрос — формальный шаг, не проверка возраста. Ребёнок создаётся родителем с логином `имя.семейныйкод`.

## 4. Развернуть серверные функции

```sh
supabase secrets set DOMASHKA_ALLOWED_ORIGINS=https://ИМЯ.pages.dev
supabase functions deploy family-admin
supabase functions deploy account-access
supabase functions deploy web-search
```

В Origin нет завершающего `/` или пути. Для нескольких реально используемых доменов задайте точный список через запятую, не `*`.

В размещённой функции обычно уже доступны `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`. Если проект использует новые API keys и прежние отключены, задайте в **секретах функции** `DOMASHKA_PUBLISHABLE_KEY` и `DOMASHKA_SECRET_KEY`. Первый — публичный ключ проекта, второй — административный secret. Не включайте административный ключ в переменные фронтенд-сборки.

`account-access` проверяет публичные действия через Turnstile и атомарные квоты; перевыпуск кодов — через JWT, действующий родительский сеанс и повторный пароль. Обе новые/обновлённые функции должны соответствовать новой миграции.

`verify_jwt = false` в `supabase/config.toml` преднамерен: функция проверяет Bearer через `auth.getUser`, затем действующий серверный сеанс/роль/семью через RPC. Отключение gateway-проверки **не означает анонимный admin API**. Не удаляйте внутренние проверки. При сбросе пароля ребёнка дополнительно проверяются текущий пароль родителя и CAPTCHA; Auth-триггер повторно проверяет одноразовое разрешение и семейную связь. Тело запроса ограничено, пароли/токены не логируются и не возвращаются в ошибках.

## 5. Собрать и опубликовать только статические файлы

Нужны Node.js 22+ и Python 3. Переменные ниже — **только публичные**. Используйте свои значения, не буквальные примеры:

```sh
npm ci
export DOMASHKA_SUPABASE_URL='https://ВАШ_REF.supabase.co'
export DOMASHKA_SUPABASE_PUBLISHABLE_KEY='ВАШ_PUBLISHABLE_ИЛИ_ANON_KEY'
export DOMASHKA_SITE_URL='https://ИМЯ.pages.dev/'
export DOMASHKA_TURNSTILE_SITE_KEY='ВАШ_ПУБЛИЧНЫЙ_SITE_KEY'
npm run build:cloud
```

PowerShell: задавайте значения через `$env:DOMASHKA_SITE_URL = '…'` и аналогично остальные. Если `python3` отсутствует, выполните `npm run build`, `python build_standalone.py`, `python scripts/prepare_cloud.py`.

Загрузите **содержимое `.cache/cloud-site`** в Cloudflare Pages (Direct Upload) либо настройте Git-сборку с указанными публичными переменными, командой `npm run build:cloud` и output directory `.cache/cloud-site`. Убедитесь, что сборка действительно установила Node/Python-зависимости. Не загружайте корень репозитория, `.env`, серверные файлы или данные пользователей. Не используйте GitHub Pages workflow для облачной сборки.

`index.html` получит публичную конфигурацию. `Domashka_PRO.html` в той же папке останется **автономным, без cloud config**; исходный отслеживаемый HTML не изменяется публикацией. `_headers` задаёт no-store, no-referrer и ограничения контента/встраивания. HTTPS-разрешения `connect-src` нужны для выбираемых пользователем AI API; не сужайте их без проверки всех сохранённых провайдеров и OCR/PDF. HTTP-адрес Ollama/моста на таком сайте блокируется mixed-content/CSP: для этого режима нужен доступный браузеру **HTTPS-мост**, не HTTP на локальном компьютере владельца сайта.

## 6. Обязательный приёмочный прогон на настоящем проекте

Сначала тестовые данные, не фотографии детей/личные сведения:

1. Зарегистрировать родителя **без email**, увидеть все **10 кодов** сразу, сохранить TXT и подтвердить сохранение. Войти на двух устройствах. Проверить Turnstile и квоты; прямой native signup должен оставаться запрещён.
2. Восстановить пароль одним кодом **на втором устройстве**: остаток 9, повтор кода запрещён, следующий работает, старые сеансы теряют доступ. Перевыпустить после текущего пароля: новый набор из 10, старые коды отменены. Потерянный ответ не повторять автоматически.
3. Создать ребёнка, проверить полный логин/пароль на ПК и телефоне, затем сброс пароля родителем с CAPTCHA.
4. Войти тем же ребёнком на двух устройствах: сохранить дневник/тетрадь/фото на первом, дождаться статуса, увидеть новую версию и загрузить её на втором. Имена/аватары/класс/ограничения должны соответствовать серверу.
5. Изменить один раздел одновременно: обе версии должны остаться до выбора, а не «последняя запись победила». Выбор облачной версии должен приостановить старый редактор до перезагрузки.
6. Отключить сеть во время редактирования. Очередь остаётся в IndexedDB; выход при несохранённой очереди не должен очищать её. После связи — отправка/конфликт, а не тихая потеря. Отдельно проверить сбой квоты/хранилища и резервную выгрузку.
7. Проверить из другой семьи/ребёнка: нельзя прочитать чужие чаты/фото, изменить роль/XP/связи или принять собственную домашку. Привязать второго родителя по одноразовому коду, затем отозвать связь.
8. «Знаю»: ошибка — 0 XP; верный ответ — +4; повтор того же ответа/карточки — без второй награды. Проверить диктовку **на физическом телефоне**, также набор текста.
9. Назначить/сдать фото/проверить домашку. Фоновое обновление не должно стирать черновик; конфликт требует выбора версии.
10. Перенести экспорт из старого HTML явно, с проверкой получателя и пометкой старых XP. Проверить, что локальные оригиналы не удалены.

Пока пункты не пройдены на опубликованном сайте, не объявляйте реальные устройства/восстановление/защищённый Storage проверенными. Живые AI-площадки и Speech API — отдельные внешние зависимости.

## Эксплуатация и ограничения реализации

- На одном браузерном origin работает **одна редактирующая вкладка** (Web Locks); ПК и телефон не блокируют друг друга. Новые входы и смена сеанса замораживают старую вкладку. Неизвестный/неподдерживаемый storage не подменяется локальной семьёй.
- Первичный вход/загрузка требуют сети. Уже открытый дневник/тетрадь может накапливать локальную очередь; это **не полная offline-first/PWA**. Семейные операции и проверка облачных карточек требуют сервера. У ребёнка без недавней проверки родительских настроек новые AI-запросы блокируются обычным интерфейсом.
- Опрос примерно раз в 15 секунд в видимой вкладке и при возврате/восстановлении сети: сначала хеши версий; неизменившиеся тетради/фото/аватары не скачиваются заново. Фото загружаются по необходимости. Это не обещание мгновенного realtime.
- CAS действует отдельно для девяти разделов настроек и каждого чата. Конфликт внутри одного списка оценок/задач требует ручного выбора; автоматического объединения отдельных пунктов пока нет.
- Секреты AI и неотправленные формы/черновики остаются на устройстве. Кэш и резервные JSON не зашифрованы ключом пользователя. На общем устройстве выходите; не полагайтесь на пароль приложения против владельца браузерного профиля.
- Сервер проверяет ответы карточек. Прочая активность — ограниченные **самоотчёты**, не защищённый от всех накруток экзамен. Родительские старые XP помечены `importedXp`; статистика не школьные оценки.
- Ограничения приложения: 20 детей/родителя, 5 родителей/ребёнка, 1000 семейных работ/ученика; до 500 КБ текста на документ, 10 МБ текста и 5000 идентификаторов документов/аккаунт **с учётом tombstones**; фото JPEG/PNG/WebP до 2 МБ. Квота проекта может закончиться раньше этих индивидуальных пределов.
- Фото неизменяемы; клиент не удаляет объекты, которые ещё могут быть нужны другой записи/устройству. Удалённый чат не гарантирует удаления объекта из Storage. Владелец организует резервное копирование и безопасную очистку с проверкой ссылок; не удаляйте квитанции наград/событий произвольно — они обеспечивают дедупликацию старых повторов. Нужны процедуры выгрузки/удаления аккаунта по запросу владельца данных.
- Для публичного использования нужны контакты оператора, информация об обработке детских данных, соответствующие согласия и оценка применимых требований приватности. Код сам по себе не является юридической/сертификационной гарантией.

## Дополнения 4.3

Новые проекты применяют все восемь SQL-файлов в порядке имён. В уже подготовленном проекте миграции повторно не выполняют: проверяйте историю. Поиск использует отдельную `web-search` функцию, owner-only Tavily key и ту же точную `DOMASHKA_ALLOWED_ORIGINS`: [контракт и квоты](AI_FEATURES.md#поиск-tavily).

Для первого Direct Upload можно собрать с `DOMASHKA_SITE_URL=auto` и `python3 scripts/prepare_cloud.py --zip Domashka_PRO_Cloudflare.zip`. Origin определяется из реального HTTPS-адреса, не из HTML-файла. Auth redirects/Origins/CAPTCHA это не настраивает: после deployment задайте точный адрес сервера по [CLOUD_LAUNCH.md](CLOUD_LAUNCH.md). Для постоянного автосборочного проекта Git-интеграцию Pages выбирайте при создании.
